> **문서 상태 (2026-11-17)**: ✅ 현행 (2026-11-16 구현) · 지도: [`docs/README.md`](../../README.md)

관련: `design-graph-multihop-chain.md` §7, `design-graph-class-query.md`, `graph-search-intended-design`(관계 SPARQL → 트리플 → 연결 청크)

## 1. 배경과 결정

이 서비스를 부르는 쪽은 둘이다.

| 호출자 | 질의 모양 | 서비스가 할 일 |
|---|---|---|
| 에이전트 (API) | 스스로 질문을 해석해 **단계별로 쪼갠 단일 질의**를 보낸다 | 질의 하나를 정확히 실행해 근거를 돌려준다. 에이전틱할 필요 없음 |
| 사람 (UI) | "빠르게 서비스를 추가하는 스타일들의 공통 약점은?" 같은 **복합 질문** | 질문을 나눠 단계별로 찾고 모아서 답한다 |

결정 (사용자, 11/16):
1. 에이전틱 처리는 **파이프라인 빌더에 등록하는 필터(스테이지) 하나**로 넣는다. 요청 옵션이 아니라 파이프라인 구성으로 켜고 끈다.
2. 에이전틱 필터는 **검색 방식을 결정하고 검색 과정을 진행**한다 (어떤 검색을 어떤 순서로 몇 번 할지).
3. 필터 UI 에 **LLM 모델 선택**을 둔다.
4. 필터가 없으면, 지금처럼 **사용자 질문을 최대한 실행 가능한 쿼리 하나로 만들어** 한 번에 검색한다.

## 2. 현재 구조 (출발점)

- 파이프라인 = `pipeline_config.stages` 의 순차 실행 (`services/retrieval/pipeline_executor.py`).
  스테이지 종류: `smalltalk`(Gate), `ann`, `bm25`, `brute_force`, `graph`, `rerank`, `ner_filter`.
- Gate(`smalltalk`)는 이미 "검색 앞단에서 흐름을 결정하는 LLM 필터" 선례다 — `api/retrieval.py` 에서 스테이지 존재 여부로 동작하고, 자기 `llm_model` 을 가진다. 에이전틱 필터는 같은 방식으로 붙인다.
- `graph` 스테이지 내부는 고정 라우팅(질문 분석 → A/B/P/H/pair/overview → 근거 없으면 V)이고 LLM 호출 지점이 고정돼 있다. 루프나 재계획은 없다 (H 의 1회 재선택만 예외).

## 3. 필터가 없을 때: 단일 실행 (기본 경로)

에이전트 호출자가 쓰는 경로이고, 사람 질문도 필터가 없으면 이 경로로 간다.

원칙: **질문 하나 → 실행 계획 하나 → 한 번 실행**. 되묻거나 반복하지 않는다.

- 지금의 `graph` 스테이지 동작 그대로가 기본이다 (분석 → 결정적 경로 → 근거 없으면 문서 검색 V).
- 보강할 것 — "질문을 최대한 실행 가능한 쿼리로":
  1. **유형 질의 + 반환 속성**: "X 인 것들의 Y" 꼴(조건으로 멤버를 고르고 그 멤버들의 특정 속성을 돌려받는 질문)을 P 계획 하나로 컴파일한다. 계획에 `filters`(멤버 조건)와 `return`(돌려받을 속성, 예: `has_weakness`)을 함께 넣어 SPARQL 한 번으로 멤버별 값을 가져온다. 지금은 멤버 선택까지만 결정적이고 속성 수집은 1-hop 확장에 기대고 있다.
  2. **값 어휘 연결**: "빠르게 서비스를 추가" 같은 표현을 스키마의 값 어휘(`release_frequency=높다`, `has_advantage ∋ 확장`)에 연결하는 단계. 실행마다 연결이 달라지는 문제(11/15 확인)를 줄인다.
  3. **집계·비교**는 계획의 `aggregate` 로 표현 가능한 것만 결정적으로 처리하고, 나머지는 V 로 넘긴다 (지금과 같음).
- 에이전트 호출자용 `answer: false`(답변 생성 없이 근거·트리플만 반환)는 이 경로의 요청 옵션으로 둔다 — 파이프라인 구성과 별개.

## 4. 에이전틱 필터

### 4.1 스테이지 정의

```jsonc
{
  "type": "agentic",
  "params": {
    "llm_model": { "provider_id": "...", "model": "glm-5.2" },  // UI 에서 선택 (Gate 와 같은 모델 선택기)
    "mode": "auto",          // auto: 복합 질문일 때만 단계 진행 / always: 항상 단계 진행
    "max_steps": 6,          // 도구 호출 상한
    "time_budget_s": 40,     // 전체 시간 상한 (넘으면 그때까지 모은 근거로 답)
    "show_steps": true       // 단계별 추론을 Execution Log 에 남김
  }
}
```

- 파이프라인에 **하나만** 둘 수 있다. 위치는 Gate 바로 뒤, 검색 스테이지 앞 (빌더가 자동 배치).
- 백엔드: `schemas/pipeline.py` 의 `type` Literal 과 `PipelineExecutor._handlers` 에 추가. 프론트: `PipelineBuilder.tsx` 의 `StageType`·스테이지 목록(새 분류 `control`)·파라미터 편집기.

### 4.2 동작

에이전틱 필터가 있으면 실행기는 나머지 스테이지를 순서대로 돌리는 대신 **제어권을 필터에 넘긴다**.
파이프라인에 등록된 검색 스테이지(`graph`, `ann`, `bm25`, `rerank` …)가 곧 **필터가 쓸 수 있는 도구 목록**이 된다 — 사용자가 빌더에서 뺀 검색은 에이전트도 쓰지 못한다. 각 스테이지의 파라미터(top_k, 모델 등)는 그대로 적용된다.

```
질문
 └─ (mode=auto) 복합 판정 ── 단순 → 기존 순차 파이프라인 실행 (§3) ─┐
      │ 복합                                                        │
      ▼                                                             │
   계획: 하위 질문·도구 순서 (LLM 1회)                               │
      ▼                                                             │
   ┌→ 도구 실행 (graph / 문서검색 / 그래프 조회 도구)                │
   │  관찰 요약 → 다음 행동 결정 (LLM)                              │
   └── 근거 충분 · max_steps · time_budget 중 하나면 종료             │
      ▼                                                             │
   근거 병합 (청크 + 트리플, 단계별 출처 유지) ◀───────────────────┘
      ▼
   답변 생성 (기존 답변 모델 — 필터 모델과 별개)
```

**복합 판정 (`mode=auto`)**: 질문 분석 결과로 판단하고, 하나라도 해당하면 단계 진행.
- 조건으로 대상 집합을 고른 뒤 그 집합에 대해 다시 묻는다 ("…하는 스타일들의 공통 약점")
- 비교·공통점·차이 ("A 와 B 의 차이", "공통적인")
- 연결 고리 질문 (H 경로 후보) 중 체인 계획이 불안정한 것
- 단일 실행(§3)이 근거 없음(V)으로 끝난 경우 — **사후 승격**: 단일 실행을 먼저 해 보고 실패하면 단계 진행

### 4.3 도구

검색 스테이지를 그대로 부르는 도구와, 그래프를 결정적으로 조회하는 도구로 나눈다. 그래프 조회 도구는 이미 있는 Fuseki 백엔드 함수(클래스 카탈로그, 유형 질의 컴파일, 체인 실행)를 감싼다. LLM 은 SPARQL 을 직접 쓰지 않는다.

| 도구 | 하는 일 | 기반 |
|---|---|---|
| `describe_kb` | 클래스·속성·값 어휘 요약 (계획 전에 1회) | `_class_catalog` |
| `find_entities(class, filters)` | 조건에 맞는 멤버 목록 | `class_query.compile_member_query` |
| `get_entity(name, properties?)` | 엔티티의 속성·관계 트리플 + 연결 청크 | 1-hop 조회 |
| `traverse(start, relations)` | 관계 체인 따라가기 | H 경로 체인 실행 |
| `graph_search(question)` | 하위 질문 하나를 기존 `graph` 스테이지로 실행 | `_execute_graph` |
| `search_documents(query)` | 문서(벡터/BM25) 검색 | `ann` / `bm25` 스테이지 |

예) "빠르게 서비스를 추가하는 스타일들의 공통 약점"
1. `describe_kb` → `release_frequency`, `modifiability`, `has_weakness` 확인
2. `find_entities(Style, release_frequency=높다 OR modifiability=높다)` → 6개
3. `get_entity(각 스타일, [has_weakness])` → 약점 트리플 + 근거 청크
4. 종료 → 답변 모델이 공통점을 정리

### 4.4 Execution Log

기존 그래프 추론 리포트와 같은 자리에 단계 목록을 남긴다 (11/15 까지의 `reasoning` 구조 재사용).
- 단계마다: 번호, 결정 이유(한 줄), 도구·인자, 결과 요약(건수, 대표 항목), 소요 시간
- 종료 사유: 근거 충분 / 단계 상한 / 시간 상한
- 단계별 근거 표시: 답변에 쓰인 청크·트리플이 몇 번째 단계에서 왔는지

스트리밍은 지금 채팅 API 가 응답을 한 번에 돌려주므로 1차 구현에서는 하지 않는다 (응답에 단계 전체 포함). 이후 SSE 로 단계별 전송.

### 4.5 모델

- 필터의 `llm_model` 은 **계획·다음 행동 결정에만** 쓴다. 답변은 기존 답변 모델(`retrieval_llm_*` → `llm_model_config`).
- 기본값: KB 의 그래프 모델. GLM 이면 `no_thinking_extra_body` 필수 (사고 모드 켜지면 호출당 30~80초).
- 구조화 출력(JSON) 으로 도구 호출을 받는다 — 공급자별 function calling 차이를 피하기 위함.

## 5. 예산과 실패 처리

- 단계당 LLM 1회 + 도구 1회. GLM 사고 끔 기준 단계당 3~6초 → `max_steps=6` 이면 최악 약 35초. 기본 `time_budget_s=40`.
- 같은 도구·같은 인자를 두 번 부르면 막는다 (반복 루프 방지).
- 도구 오류 → 관찰에 오류를 넣고 계속. 연속 2회 실패면 종료하고 단일 실행 결과로 대체.
- 근거 0 으로 끝나면 문서 검색(V) 결과로 답한다 — 기존 원칙(근거 없으면 문서 검색)과 같음.

## 7. 구현 순서

1. 도구 함수 정리 (Fuseki 백엔드의 기존 함수를 도구 인터페이스로 감싸기) + 단위 테스트
2. `agentic` 스테이지 스키마·실행기 연결, 루프(계획 → 도구 → 관찰 → 종료) 구현
3. Execution Log 단계 리포트
4. 파이프라인 빌더 UI (스테이지 추가, 모델 선택기, mode/max_steps/time_budget)
5. §3 단일 실행 보강 (반환 속성 계획, 값 어휘 연결) — 필터 없는 경로 품질
6. §6 검증, 결과를 `design-graph-multihop-chain.md` 처럼 평가 기록으로 남김

## 8. 1차 구현 결과 (2026-11-16)

### 8.1 설계와 다르게 한 것

- **도구는 등록된 검색 스테이지만** (`graph_search` / `vector_search` / `keyword_search`). §4.3 의 세부 그래프 도구
  (`find_entities`, `get_entity`, `traverse`)는 만들지 않았다. graph 스테이지에 하위 질문을 넣으면 기존 결정적 경로
  (유형 질의 P, 체인 H, 1-hop A …)가 그대로 처리하므로, 에이전트는 **질문을 나누고 순서를 정하는 일만** 한다.
  세부 도구는 단계 수가 많아지는 문제가 보일 때 추가한다.
- `describe_kb` 는 도구가 아니라 계획 프롬프트에 처음부터 넣는다 (유형·멤버 예시·속성과 값 어휘, 긴 서술 값은 예시 하나만).
- 한 단계에 독립 하위 질문을 최대 4개 **동시에** 실행 (대상별 속성 조회).
- auto 사후 승격(단일 실행이 근거 없이 끝남)은 **최대 2단계**만 — 문서에 없는 사실을 오래 찾지 않게. 계획 규칙에도
  "표현만 바꿔 두 번 찾아 없으면 종료" 를 넣었다.
- 시간 예산은 파이프라인 시작 기준 (승격 전 단일 실행 포함). 남은 시간이 8초 미만이면 새 단계를 시작하지 않고,
  하위 검색 하나는 최대 20초.
- 답변 컨텍스트 맨 앞에 "검색 과정 + 모든 단계 결과를 합쳐 답할 것" 을 넣는다 — 처음에 답변 모델이 일부 단계만
  보고 답한 문제(대상 6개 중 3개만 다룸) 때문.
- Execution Log 모드 표시 `AG`.

파일: `backend/app/services/retrieval/agentic.py`, `pipeline_executor.py`(`_execute_agentic`·`_run_sequential`),
`schemas/pipeline.py`, `frontend/src/components/PipelineBuilder.tsx`(Agentic 카드: 모델·mode·Max Steps·Time),
테스트 `backend/tests/test_agentic.py`.

### 8.2 검증

**"사용자가 원하는 서비스를 빠르게 추가하는 스타일들이 가지는 공통적인 약점은?"** (test-ontology, glm-5.2)

| | 단일 실행 (필터 없음) | 에이전틱 auto |
|---|---|---|
| 과정 | 유형 질의 1회 (`modifiability=high` → 3개) | ① 조건 2개로 대상 찾기 (service_count, release_frequency → 4개) ② 대상별 `tradeoffs.cons` 4건 동시 조회 ③ 운영 복잡도 확인 |
| 답 | 3개 스타일의 공통 약점 | 4개 스타일 각각의 단점 + 공통 약점(운영·설계 복잡도, 지연, 추가 실패 지점) |
| 시간 | 31초 | 57초 |

남은 문제: "빠르게 추가" 를 어떤 속성으로 해석하는지가 실행마다 달라진다 (modifiability / release_frequency / service_count).
§3 의 값 어휘 연결 단계로 줄여야 한다.

## 9. 스크래치패드 (2026-11-16)

**문제** — "배포 용이성과 수정 용이성이 좋은 스타일은?" (test-ontology, Agentic + Graph): 조건별 후보는 찾았지만
(1) 시간 상한(40초)으로 교차 확인 전에 끝났고 (2) 수정 용이성을 `fit_signals` 에서만 찾아 `quality_attributes` 의
Microservices modifiability 를 놓쳤으며 (3) 단계 사이에 "무엇이 확인됐는지"가 남지 않아 교집합을 추적하지 못했다.

**스크래치패드** — 계획 LLM 이 매 단계 고쳐 쓰는 메모 (JSON `scratchpad`, 마크다운, 최대 2,500자):
`## 알게 된 것`(출처 단계) / `## 후보 × 조건`(조건이 둘 이상이면 표, ✔ 근거 있음 · ✘ 반대 근거 · ? 미확인) / `## 아직 모르는 것` / `## 다음`.
- 다음 단계 프롬프트에 직전 메모를 넣어 이어 쓰게 한다.
- 규칙: 표에 ? 가 남으면 finish 하지 말고 그 칸을 채우는 검색을 먼저. 한 조건이 KB 의 **여러 위치**(적합 신호·품질 속성 목록 등)에 있을 수 있으니 한 곳에 없다고 ✘ 로 두지 말 것. 반대 근거(effect=negative)는 ✘.
- 근거 충분으로 끝나지 않으면(시간·단계 상한, 반복) **정리 호출** 1회(검색 없이, 25초 상한)로 최종 메모를 만든다.
- 최종 메모를 답변 컨텍스트 맨 앞에 넣는다 — "✔/✘/? 를 지켜 답하고 ? 는 확인되지 않음으로 밝힐 것".
- 화면: 검색 결과의 추론 카드가 `Agentic 추론 과정` 으로 바뀌어 최종 스크래치패드(표 색 구분), 단계별 계획·호출·관찰, 단계 시작 시 메모를 보여 준다 (`AgenticScratchpad.tsx`). Execution Log 에도 `[Agentic] 스크래치패드` 로 남는다.
- 기본 시간 상한 40 → 60초.

**결과 (같은 질문)** — 3단계, 후보 × 조건 표: Micro-Frontend ✔✔, Microservices ✔(품질 속성)✔(적합 신호), 나머지는 한쪽 ?.
답변: **Micro-Frontend, Microservices** (정답), ? 후보는 "확인되지 않음" 으로 명시.

남은 점: 하위 검색 일부가 16~20초라 60초에도 시간 상한(전체 91초). 3단계에서 조회한 modular_monolith(deployability negative)가
정리 메모에 ✘ 로 반영되지 않고 ? 로 남음 — 관찰 요약이 효과값(effect)을 충분히 담지 못하는 것으로 보임. 다음 과제: 관찰 요약에
조건 값(effect·strength) 포함, 하위 검색 속도.
