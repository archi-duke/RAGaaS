## D1. 응답 속도 = 스트리밍 + 질의 계획 선행 실행 + LLM 동시 호출 제한

- **문제**: 첫 글자까지 14.4초 ("14.4 도 느린데...").
- **결정**: `/chat/stream` SSE 답변 스트리밍, 유형 질문이면 질의 계획을 분석과 겹쳐 선행 실행, LLM 호출은 호스트당 동시 4개 + 429 재시도 3회.
- **결과**: 첫 글자 14.4초 → 약 9초. Z.ai 는 동시 8개에서 429.
- **참조**: PR #60
- **후속 판단**: 외부 에이전트가 MCP 로 쓰면 스트리밍 효과는 작다 (사용자와 합의, 내부 채팅용으로 유지).

## D2. 외부 에이전트용 MCP — 클라이언트가 질의 계획을 쓰고 RAGaaS 는 검증·실행만

- **사용자 제안**: "호출하는 에이전트가 아예 SPARQL 을 생성해서 보내면 좀 개선될까?"
- **검증**: test-ontology2 를 직접 조회해 '유지보수성이 좋은 스타일' 류 질문으로 확인.
- **결정**:
  - 클라이언트 에이전트가 스키마(describe)를 받아 **query_plan JSON** 을 작성 → RAGaaS 는 검증·SPARQL 컴파일·실행 (RAGaaS 쪽 LLM 0).
  - 외부 계약은 **query_plan 하나**. SPARQL·Cypher 는 RAGaaS 가 만든다 → Neo4j 를 붙여도 클라이언트 무변경.
  - 원문 SPARQL 엔드포인트는 관리자·디버그 전용 (`AGENT_SPARQL_ENABLED`).
  - 운영 = 사내 폐쇄망. 안전장치 = 읽기 전용 + 범위·자원 제한.
  - GoJIRA 는 이 방식으로 전환. Neo4j 는 최종 지원 대상 (우선 Fuseki).
- **폐기한 대안**: 클라이언트가 SPARQL 을 직접 생성 — 저장소 종속(Neo4j 불가), 쓰기·과부하 위험, 검증 불가.
- **ADR**: ADR-004 (11/17 기록)
- **설계서**: `design/agent/design-mcp-agent-query.md` · PR #61 (P1 REST, P2 query_plan, P3 MCP `/api/mcp`, P4 스킬 `skills/ragaas-query`)

## D3. query_plan 은 자동 완화하지 않는다

- **결정**: 결과 0건이면 `zero` 와 이유(값 표기·경로)를 돌려주고, 완화는 클라이언트가 판단한다. 조회 실패는 `status: error` 로 분명히 (빈 결과로 숨기지 않음).
- **이유**: 외부 에이전트는 스스로 다시 질의할 수 있고, 서버의 암묵적 완화는 답을 넓혀 오답이 된다.

## D4. KB 용어 사전 — 적재 시 LLM 1회, 검색은 사전만, 번역은 클라이언트

- **문제**: 한영 표기 차이·동의어·상위 개념 ("한계점에 대한 근본적 대책이 필요하겠는데").
- **결정**:
  - 적재 후 LLM 이 라벨마다 한/영/음역/동의어/상위 개념을 한 번 만든다. 검색 시점에는 사전 조회만.
  - 사전에 없으면 **클라이언트가 보낸 영어 표기(term_en)** 로 영어 임베딩 비교 (번역 대체 단계).
  - 원문 라벨은 그대로 두고 사전이 다국어 축을 맡는다.
- **폐기한 대안**: 엔티티·관계를 영어로 저장하고 답만 질의 언어로 — 원문 표기 손실. 실시간 한↔영 임베딩 유사도 — 짧은 단어는 신뢰 불가 (장점~pros 0.20).
- **설계서**: `design/agent/design-kb-lexicon.md` · PR #61, #62 (L3 편집 탭, L4 자동 갱신·내부 검색 연결)

## D5. GoJIRA 변경은 GoJIRA 담당 세션에 맡긴다

- **결정**: "직접 수정하지 말고 고지라를 담당한 에이전트 … 그 에이전트한테 맡겨야 돼". style-define 엔진을 query_plan 호출로 바꾸는 일은 GoJIRA 세션이 PR #133·#134 로 수행.
- **GoJIRA 요청 반영**: 조건 상한 12 → 64, `in` 의 목록 밖 값은 빼고 평가, 조회 실패는 `status: error`.

## D6. 데이터 품질 D1 — 관계 방향: 확실한 반대만 자동, 나머지 검토

- **결정 (사용자 "권장하는 대로")**: 같은 클래스끼리 잇는 관계를 원문으로 판정, 사용자 승인 35건 뒤집기. 이후 새 트리플은 증분 검증하고 **반대 + 양끝이 한 문장 + 2차 확인 일치** 일 때만 자동 뒤집기.
- **경위**: 승인 35건 중 1건(케플러 법칙→만유인력)과 자동 1건(헬름홀츠→헤르츠)이 오판 → 되돌리고 2차 확인을 추가. 엇갈린 6건은 사람 검토.
- **데이터만이 아니라 모듈로**: "비슷한 유형이 와도 제대로 분류될 수 있도록" → 재추출·그래프 변경 후 자동 실행.

## D7. 데이터 품질 D2·D3 — 중복은 LLM 제안 + 사람 검토 일괄 병합, range 위반은 AI 추천 적용

- **결정**: 중복 후보 39 중 30묶음 병합, 남은 28묶음은 용어 사전 탭에서 사람 검토. range 위반 AI 추천 11건 적용.
- **드러난 결함**: 병합 정규화 버그 3건(이름 규칙 체인, 트리플 규칙 보존, 클래스 승계) → 수정.

## D8. 평가 전략 = 단계별 좁은 확인 + 마지막 전체 평가 2회

- **결정 (사용자)**: 단계마다 전체 39×2 평가를 돌리지 않는다. 결정적 확인 + 영향 문항만 확인하고, 끝에 전체 2회.
- **이유**: 평가 잡음 ±2~3점이 단계 효과(1~2점)보다 크다. 변경은 규칙으로 남아 되돌릴 수 있다.
- **번복 조건**: 최종 평가에 문제가 있으면 단계별 전체 평가로 돌아간다.

## D9. 적재 모델 gpt-4o-mini → glm-5.2 (온톨로지 KB 3개)

- **결정**: "적재모델 바꿔 … Z.ai로해". test-ontology, test-ontology2, test-ontology3.
- **대가**: 재추출 동시 호출 8개가 Z.ai 429 → 적재 서비스에도 동시 4 + 429 재시도 (da885da). 이후 429 0건.
- **결과**: 물리학사 파이프라인 31.5 → 35.5, GLM 에이전트 35 → 37.5 (D1~D3 포함, 당시 채점 기준). 평가 README 16.
