# 스키마 편집기 사용 설명서

대상: 지식베이스(KB)의 스키마를 확인하고 다듬는 사람. 온톨로지를 처음 다뤄도 따라 할 수 있게 개념부터 설명한다.
위치: KB 상세 화면 → **Schema** 탭 (온톨로지로 승격된 KB 에만 보인다).
설계 문서: `docs/design-schema-editor.md` · 스키마 추출 절차: `.claude/skills/ontology-schema-extraction/SKILL.md`

---

## 1. 먼저 알아 둘 개념

### 1.1 그래프와 트리플

RAGaaS 는 문서를 읽어 **"주어 — 관계 → 목적어"** 한 줄짜리 사실로 쪼개 저장한다. 이 한 줄을 **트리플**이라 부른다.

```
아인슈타인 ——제안함——▶ 특수상대성이론
Microservices ——has_negative_effect_on——▶ 운영 복잡도
```

트리플이 모이면 점(엔티티)과 화살표(관계)로 된 **그래프**가 된다. 검색은 이 그래프에서 질문에 맞는 화살표를 따라가 답을 찾는다.

### 1.2 스키마 = 그래프의 설계도

그래프 안의 수많은 점과 화살표가 "어떤 종류이고 어떻게 이어질 수 있는지"를 적은 것이 **스키마**다.
데이터 하나하나가 아니라 **종류**를 다룬다.

| 데이터(그래프) | 스키마 |
|---|---|
| 아인슈타인, 보어, 파인만 | **Person** 클래스 |
| 특수상대성이론, 양자역학 | **TheoryOrConcept** 클래스 |
| 아인슈타인 —제안함→ 특수상대성이론 | **제안함**: Person → TheoryOrConcept |

스키마가 정확하면 검색이 "인물이 제안한 이론" 같은 질문을 정확한 화살표로 풀 수 있다. 스키마가 틀리거나 비어 있으면
검색은 문서 전체에서 비슷한 문장을 찾는 방식으로 물러난다(느리고 덜 정확).

### 1.3 클래스와 멤버

- **클래스**: 같은 종류의 대상을 묶은 이름. 예) Person, ArchitectureStyle, QualityAttribute
- **멤버**(인스턴스): 클래스에 속한 실제 대상. 예) ArchitectureStyle 의 멤버 = Microservices, Hexagonal …
- 이 화면의 **멤버 수**는 "이 클래스로 지정된 엔티티 수"다.
- 구조화(YAML/JSON) KB 에서는 클래스를 **유형**이라고 부른다 (§4).

> 클래스가 **아닌** 것: 문장("규율을 유지하기 어렵다"), 점수·수치("-3점"), 한 대상에 붙은 정보 묶음, '결과'·'이 실험' 같은 조각.

### 1.4 속성: 관계와 값 속성

스키마의 **속성**은 화살표의 종류다. 화살표가 가리키는 쪽(목적어)이 무엇이냐에 따라 두 가지로 나뉜다.

| 구분 | 목적어 | 예 | 화면 표시 |
|---|---|---|---|
| **관계** | 다른 클래스의 멤버 | 아인슈타인 —제안함→ 특수상대성이론(TheoryOrConcept) | range 에 클래스 이름, 그래프에 클래스 사이 화살표 |
| **값 속성** | 문장·수치·등급 | Microservices —운영_복잡도→ "높음" | range 빈칸, 그래프에서 클래스 안 목록 |

### 1.5 domain 과 range — 화살표의 방향

관계에는 방향이 있다.

```
domain ——관계——▶ range
(주어 쪽 클래스)      (목적어 쪽 클래스)

Person ——제안함——▶ TheoryOrConcept
```

- **domain**: 화살표가 **출발**하는 클래스 (주어가 속한 클래스)
- **range**: 화살표가 **도착**하는 클래스 (목적어가 속한 클래스)
- range 가 비어 있으면 그 속성은 값 속성으로 취급된다.

방향이 틀리면 검색이 반대로 따라간다. 예) "B는 A의 지도로 학위를 받았다"는 **A —지도함→ B** 다 (문장의 주어 B 가 아니라 지도한 A 가 출발점).

### 1.6 정의와 별칭

- **정의**: 속성의 뜻을 한 문장으로. `Domain | 속성 | Range — 설명` 꼴로 쓰면 방향까지 전달된다.
  예) `Person | 제안함 | TheoryOrConcept — 인물이 이론·개념을 처음 제시하거나 정식화함`
  정의는 **재추출**(§1.9) 때 LLM 프롬프트에 그대로 들어간다. 정의가 정확할수록 다시 뽑는 트리플이 정확해진다.
- **별칭**: 같은 뜻의 다른 이름. 예) `제안함` 의 별칭 = 제안, 제안했다, 정식화, 제시
  문서마다 다르게 뽑힌 관계 이름을 대표 이름 하나로 모은다. 같은 별칭을 두 속성에 넣을 수 없다.

### 1.7 시드

사람이 처음에 정해 준 핵심 어휘(클래스·속성 이름, 정의, 방향). 시드가 있으면 LLM 이 그 이름과 방향을 따른다.
화면에서 속성 이름 아래 **"시드"** 표시가 붙는다. 데이터 검증은 시드 range 를 자동으로 지우지 않는다.

### 1.8 규칙 — 스키마가 데이터에 적용되는 방식

편집 내용은 아래 **규칙**으로 저장되어 그래프에 적용된다 (Documents 탭 → 스키마 정렬에서 목록 확인·삭제 가능).

| 규칙 | 뜻 | 예 |
|---|---|---|
| class | 엔티티 → 클래스 지정 | 단순성 → QualityAttribute |
| key | 관계 이름 → 대표 이름 | 제안했다 → 제안함 |
| entity | 엔티티 이름 → 대표 이름 (병합) | scalability → 확장성 |
| value | 값 표기 통일 | medium_or_higher → medium |

### 1.9 리플레이와 재추출

| | 리플레이 | 스키마 기준 재추출 |
|---|---|---|
| 하는 일 | 이미 뽑아 둔 트리플에 **규칙만 다시 적용** | 저장된 문서 조각을 LLM 이 스키마(정의·방향)를 보고 **다시 읽어** 트리플을 새로 뽑음 |
| 비용 | 없음 (몇 초~수십 초) | 문서 조각마다 LLM 호출 (분 단위, 비용 있음) |
| 언제 자동 | 이름 변경 저장, 멤버 지정, 표기 병합 | 자동 아님 — 직접 실행 |
| 반영되는 것 | 이름·분류·병합 | 정의·방향·새 속성 |

### 1.10 일치율 — "무엇에 대한 일치인가"

속성 표의 방향 칸 아래 **"일치 77% / 31"** 같은 표시는:

> **이 관계의 목적어(화살표가 가리키는 쪽) 가운데, range 로 지정한 클래스의 멤버인 것의 비율** / 판정에 쓴 서로 다른 목적어 수

예) `has_positive_effect_on` 의 range = QualityAttribute 이고 목적어가 31종일 때

```
Microservices ——has_positive_effect_on——▶ 변경 용이성   (QualityAttribute 멤버 ✔)
Microservices ——has_positive_effect_on——▶ 관측성        (QualityAttribute 멤버 ✔)
Serverless    ——has_positive_effect_on——▶ 단순성        (클래스 없음 ✘ → 멤버 누락 후보)
...
31종 중 24종이 QualityAttribute 멤버 → 일치 77% / 31
```

- 일치율이 높으면(60% 이상, 초록) 스키마와 데이터가 맞다.
- 낮으면(주황) 둘 중 하나다: **range 가 틀렸거나**, 목적어가 맞는 종류인데 **클래스 지정이 빠졌거나**(멤버 누락, §3.3).
- 판정에서 빼는 목적어: 문장, 숫자로 시작하는 값('-3점'), 30자 넘는 이름. 서로 다른 목적어가 **5개 미만**이면 판정하지 않는다(표시 안 함).
- **계열**: `has_positive_effect_on`, `has_negative_effect_on`, `has_strong_negative_effect_on` 처럼 부호·강도만 다른 관계는
  목적어를 **합쳐서** 판정한다 (마우스를 올리면 합친 관계 목록이 보인다). 한쪽 목적어만 분류돼 있어도 같은 range 를 받게 하려는 것.

**"추천: → X (p%)"**: range 가 비어 있는데 목적어의 p% 가 클래스 X 의 멤버라는 뜻. 누르면 range 칸에 X 가 들어간다.
**"데이터는 → X (p%)"**: 지정한 range 와 데이터가 지지하는 클래스가 다르다는 경고.

판정 기준 요약:

| 상황 | 결과 |
|---|---|
| 한 클래스가 목적어의 60% 이상 | 그 클래스가 range 로 추천·채택 (LLM 이 정한 range 는 교체, 시드·사람이 정한 range 는 경고만) |
| 지정한 range 의 일치율 30% 미만 | LLM 이 정한 range 는 비움, 시드·사람이 정한 것은 경고 + 멤버 누락 점검 |
| 그 사이 | 유지, 멤버 누락 후보로 보강 |

## 2. 화면 구성

```
┌ 스키마 편집  버전 4 · 2026-11-16 · 클래스 6 · 속성 38   [뷰어에서 열기][다시 불러오기][스키마 기준 재추출…][저장] ┐
│ 안내 문구                                                                                              │
│ ┌ 변경: … / 오류 / 경고 ┐   ← 편집할 때마다 서버가 검증한 결과                                            │
│ ┌ 데이터 검증 ┐            ← 멤버 누락 · 표기 중복 · range 위반 (텍스트 KB)                               │
│ [표][그래프]                                                                                          │
│ ┌ 클래스 표 ┐ ┌ 속성 표 ┐  또는  ┌ 그래프 ┐                                                           │
│ ┌ 스키마 밖 관계 ┐  ┌ 이력 ┐                                                                          │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

| 요소 | 설명 |
|---|---|
| 버전 | 저장할 때마다 1씩 오른다. 다른 사람이 먼저 저장했으면 저장이 거부된다 → **다시 불러오기** 후 다시 편집 |
| 뷰어에서 열기 | 저장된 스키마를 큰 그래프 뷰어(새 탭)로. 클래스를 누르면 실제 멤버가 펼쳐진다 |
| 스키마 기준 재추출… | 재추출 창(비용 견적·진행·되돌리기). 텍스트 KB 에만 |
| 저장 | 변경이 있고 오류가 없을 때만 눌린다 |
| 변경·오류·경고 | 저장 전 미리보기. 오류(빨강)는 저장을 막고, 경고(주황)는 저장은 되지만 확인 권장 |

### 2.1 클래스 표

| 열 | 설명 |
|---|---|
| 이름 | 영어 PascalCase 권장 (Person, QualityAttribute). 바꾸면 아래에 "이전: …" 표시 |
| 설명 | 한 문장 정의 |
| 멤버 | 지정된 멤버 수 (마우스를 올리면 예시 — 구조화 KB) |
| 🗑 | 삭제 — 이 클래스로 지정된 멤버 규칙이 꺼진다 (엔티티 자체는 남음) |

### 2.2 속성 표

| 열 | 설명 |
|---|---|
| 이름 | 속성 대표 이름. "시드" = 사람이 정한 어휘 |
| 방향 (domain → range) | 출발 클래스 선택 → 도착 클래스(또는 빈칸 = 값 속성). 아래에 일치율·추천 (§1.10) |
| 정의 | 재추출 프롬프트에 그대로 들어간다 |
| 별칭 | 쉼표로 구분 |
| 트리플 | 그래프에서 이 속성을 쓰는 트리플 수 |
| 🗑 | 스키마에서 삭제 — 기존 트리플은 남고 '스키마 밖 관계'로 분류 |

위쪽: **검색창**(이름·별칭·정의), **range 추천 모두 적용**(추천이 있을 때), **속성 추가**.

### 2.3 그래프 보기

**[그래프]** 를 누르면 지금 편집 중인 스키마를 그림으로 본다 (저장 전 변경도 반영).

| 표시 | 뜻 |
|---|---|
| 파란 큰 점 | 클래스(유형). 이름 옆 (숫자) = 값 속성 수 |
| 이름 붙은 화살표 | 관계 (domain → range). 같은 두 클래스 사이 여러 관계는 곡선으로 나뉜다 |
| 고리 화살표 | 자기 관계 (ArchitectureStyle → ArchitectureStyle, 예: 관련_패턴) |
| 주황 점 "domain 미지정" | 출발 클래스가 없는 속성 모음 — 고칠 곳 |
| 회색 작은 점 | 값 속성 ("값 속성도 노드로"를 켰을 때) |
| 청록 점 | 중첩 블록 (구조화 KB 에서 "중첩 블록 펼치기"를 켰을 때) |

점을 누르면 오른쪽 패널에 설명, 나가는·들어오는 관계, 값 속성 목록(정의·별칭·값 예시)이 나온다. 화살표를 누르면 그 관계의 정의가 나온다.

**그래프에서 볼 것**: 어떤 화살표에도 연결되지 않은 클래스(쓸모가 없거나 range 누락), "domain 미지정" 노드, 이상하게 많은 관계가 몰린 클래스.

### 2.4 스키마 밖 관계

그래프에는 있는데 스키마에 없는 관계 이름 (트리플 수 순). 의미 있는 것은 눌러서 속성으로 추가하고, 기존 속성의 다른 표기면 그 속성의 별칭에 넣는다.

### 2.5 이력

저장할 때마다 바꾸기 **전** 스키마가 남는다 (최근 20개). **되돌리기**는 그 버전을 새 버전으로 저장한다 (이력이 지워지지 않음). 그 사이 바꾼 이름도 규칙과 그래프까지 함께 되돌린다.
스키마를 다시 유도(Promote)해도 직전 스키마가 이력에 남는다.

## 3. 데이터 검증 카드 (텍스트 KB)

LLM 이 만든 스키마를 그대로 믿지 않고, 그래프 데이터로 확인한 결과다. **모든 제안은 사람이 체크해야 적용된다.**

### 3.1 멤버 누락

range 클래스로 이어지는 관계의 목적어인데 **아무 클래스에도 지정되지 않은 엔티티**. 클래스별로 칩으로 보인다 (숫자 = 등장 수, 마우스를 올리면 어떤 관계에서 나왔는지).

1. 실제로 그 클래스에 속하는 것만 체크한다. **"여러 번 나온 것 선택"** 으로 시작하면 빠르다.
2. **체크하지 말 것**: 문장 조각('기술적으로', '조직 측면에서 요구되는 전제는 없다'), 등급 값('중간', '높음'), 점수.
3. **"선택 N개를 X 멤버로"** → class 규칙이 만들어지고 리플레이된다. 일치율이 올라간다.

### 3.2 표기 중복 찾기

한 클래스의 멤버·후보 안에서 같은 개념을 다르게 적은 것(한국어/영어, 약어)을 LLM 이 찾아 **제안**한다.

- 묶음마다 체크 → **"체크한 묶음 병합"** → entity 규칙 + 리플레이. 대표 이름(굵게)으로 합쳐진다.
- **반대 개념을 같은 것으로 묶는 경우가 실제로 있다.** 예) '디버깅 용이성' ← 'debugging complexity' (용이성 ↔ 복잡도), '운영 단순성' ← '운영 복잡도'. 반드시 읽고 체크를 푼다.
- '확장성' 과 '확장성 요구' 처럼 품질과 요구사항은 다른 개념이다.

### 3.3 range 위반

목적어가 range 와 **다른 클래스**의 멤버인 경우 (접혀 있음). 예) `has_positive_effect_on` 의 목적어에 `Microservices`(ArchitectureStyle) — 추출이 잘못됐거나 방향이 뒤집힌 트리플이다.
지금은 표시만 한다. 많이 나오면 range 가 틀렸는지, 그 클래스 분류가 틀렸는지 확인한다.

## 4. 구조화(YAML/JSON) KB 에서 다른 점

YAML 은 필드 구조가 곧 스키마라, 업로드할 때마다 스키마가 다시 만들어진다. 편집 내용은 따로 저장해 두었다가 매번 덧씌운다 → **다시 올리거나 새 문서를 넣어도 유지된다.**

| 할 수 있는 것 | 저장 방식 |
|---|---|
| 유형 이름·설명 (K1 → ArchitectureStyle) | 덧씌우기 |
| 속성 정의·별칭 | 덧씌우기 |
| 속성 이름(필드 경로) 변경 (`tradeoffs.cons` → `tradeoffs.weaknesses`) | key 규칙 + 해당 문서 재처리 |
| ✘ 속성·유형 추가, 삭제, 방향 변경 | YAML 원본에서 |

- **유형 이름이 K1, K2…** 로 보이면 자동으로 붙은 이름이다. 알아보기 쉬운 이름과 설명을 붙이면 검색 계획에도 쓰인다.
- **속성 = 필드 경로**: `fit_signals.modifiability` 는 YAML 의 `fit_signals:` 아래 `modifiability:` 필드.
- **중첩 블록**(`fit_signals:`, `tradeoffs:`)은 클래스가 아니라 한 레코드에 붙은 정보 묶음이다. 그래프에서는 유형 안의 값 속성으로 접혀 보인다 ("중첩 블록 펼치기"로 펼침).
- **"→ ArchitectureStyle (다른 레코드 참조)"**: 값이 다른 레코드를 가리키는 필드 (`related_patterns: [hexagonal, cqrs]`). 그래프에서 유형 사이 관계로 그려진다.
- 표의 **레코드** 열 = 그 필드를 가진 레코드 수. 데이터 검증 카드와 재추출은 없다.

## 5. 자주 하는 작업

### 5.1 처음 열었을 때 점검 (10분)
1. **[그래프]** 로 전체 모양을 본다 — 고립된 클래스, "domain 미지정", 화살표가 하나도 없는 KB 는 range 누락 의심.
2. **데이터 검증 카드**에서 멤버 누락을 정리한다 (§3.1).
3. 속성 표에서 **일치율이 주황**인 관계를 본다 → range 가 맞는지, 멤버 누락인지 판단.
4. **정의가 빈** 속성을 채운다 (저장 시 경고로 목록이 나온다).
5. 저장.

### 5.2 관계 이름 바꾸기
이름 칸을 고치고 저장 → 옛 이름의 트리플이 새 이름으로 옮겨진다 (리플레이, 비용 없음). 되돌리기도 가능.

### 5.3 방향(domain/range) 고치기
방향 칸을 고치고 저장 → 스키마·검색 계획에는 바로 반영된다. **이미 뽑힌 트리플의 방향은 바뀌지 않는다** — 데이터까지 고치려면 **스키마 기준 재추출**.

### 5.4 range 채우기
- 추천 버튼이 있으면 눌러서 확인 후 저장 (또는 "range 추천 모두 적용").
- 추천이 없는데 의미상 클래스로 이어져야 하면 직접 넣고 저장 → 일치율이 낮게 나오면 멤버 누락을 정리한다.

### 5.5 정의를 다듬었을 때
정의·별칭·새 속성은 스키마에는 바로 저장되지만 **데이터에는 재추출해야 반영**된다. 여러 개 고친 뒤 한 번에 재추출하는 게 비용상 낫다.

### 5.6 잘못 저장했을 때
**이력 → 되돌리기**. 멤버 지정·병합 규칙은 Documents 탭 → 스키마 정렬 → 규칙 목록에서 지울 수 있다 (지운 뒤 리플레이).

## 6. 자주 묻는 질문

**Q. 저장했는데 검색 결과가 그대로예요.**
이름·분류 변경은 리플레이로 바로 반영된다. 정의·방향 변경은 재추출해야 데이터가 바뀐다. 또 검색은 클래스 목록을 최대 5분 캐시한다(저장하면 비워진다).

**Q. 일치율이 안 보이는 관계가 있어요.**
서로 다른 목적어가 5개 미만이면 판정하지 않는다. 데이터가 적은 관계는 사람이 의미로 판단한다.

**Q. LLM 이 만든 정의를 믿어도 되나요?**
초안이다. 특히 방향(`A | 관계 | B` 에서 A 와 B)을 확인한다. 정의는 재추출 품질을 좌우한다.

**Q. 관계 여러 개가 거의 같은 뜻인데 합쳐야 하나요?**
같은 뜻이면 한쪽을 대표로 두고 다른 쪽을 별칭으로 넣는다. 단, **부호·강도만 다른 관계**(positive / negative / strong_negative)는 합치지 않는다 — 합치면 강도 정보가 사라진다. 같은 range 를 주는 것으로 충분하다.

**Q. 클래스를 삭제하면 데이터도 지워지나요?**
아니다. 그 클래스로 지정한 규칙만 꺼진다. 엔티티와 트리플은 남는다.

**Q. 평가용 KB 에서 스키마를 다시 유도해도 되나요?**
먼저 미리보기(`POST /knowledge-bases/{kb}/schema/induce/dry-run`)로 무엇이 바뀌는지 본다. 재유도는 직전 스키마를 이력에 남기지만, 규칙이 다시 만들어져 검색 결과가 달라질 수 있다.

## 7. 용어 정리

| 용어 | 뜻 |
|---|---|
| 트리플 | 주어 — 관계 → 목적어 한 줄짜리 사실 |
| 엔티티 | 그래프의 점 (사람·이론·스타일 등) |
| 클래스 / 유형 | 엔티티의 종류 (구조화 KB 에서는 유형) |
| 멤버 | 클래스에 속한 엔티티 |
| 관계 | 목적어가 다른 클래스의 멤버인 속성 (클래스 사이 화살표) |
| 값 속성 | 목적어가 문장·수치·등급인 속성 |
| domain / range | 관계의 출발 클래스 / 도착 클래스 |
| 일치율 | 관계 목적어 중 range 클래스 멤버의 비율 |
| 멤버 누락 | range 로 이어지는데 클래스가 지정되지 않은 목적어 |
| range 위반 | 목적어가 range 와 다른 클래스의 멤버 |
| 계열 | 부호·강도만 다른 관계 묶음 (일치율을 함께 판정) |
| 별칭 | 같은 뜻의 다른 이름 |
| 시드 | 사람이 정한 핵심 어휘 |
| 규칙 | 스키마를 데이터에 적용하는 저장 단위 (class/key/entity/value) |
| 리플레이 | 저장된 트리플에 규칙만 다시 적용 (비용 없음) |
| 재추출 | 문서를 LLM 이 스키마를 보고 다시 읽어 트리플을 새로 뽑음 (비용 있음) |
| TBox | 저장된 스키마 그래프 (뷰어에서 보는 것) |
| 승격·유도 | 그래프를 보고 LLM 이 스키마 초안을 만드는 단계 (Promote 탭) |
| 중첩 블록 | YAML 의 하위 묶음 (`fit_signals:`) — 클래스가 아님 |
