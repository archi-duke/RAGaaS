# 운영 참고: 스키마 품질과 잘못된 답변 위험

작성일: 2026-11-16
관련: `docs/guide-schema-editor.md`(스키마 편집기 사용 설명서), `docs/design-schema-editor.md`(설계)

온톨로지 KB 를 운영하면서 자주 나올 두 질문에 대한 정리다.

1. range 위반·멤버 누락이 남아 있으면 서비스를 막아야 하나?
2. 스키마와 맞지 않는 트리플 때문에 잘못된 답을 하지는 않나?

---

## 1. range 위반·멤버 누락이 있으면 서비스를 막아야 하나?

**막지 않는다.** 대신 *나빠진 스키마가 검토 없이 서비스에 나가는 것*을 막는 쪽이 맞다.

### 막지 않는 이유

1. **스키마는 100% 맞을 수 없다.** 문서가 추가되고 새 표기·새 사실이 들어오면 멤버 누락은 다시 생긴다. 0건이 될 때까지 막으면 서비스를 열 수 없다.
2. **검색은 무너지지 않게 만들어져 있다.** 그래프 경로로 근거를 못 찾으면 문서 검색(V)으로 넘어간다. 영향은 그 관계를 쓰는 질문에 국한되고, 대부분 "틀린 답"보다 "덜 찾은 답"이 된다.
3. **두 문제의 영향이 다르다.**

| | 검색에 주는 영향 | 심각도 |
|---|---|---|
| 멤버 누락 | 유형 질의("Requirement 중 …")에서 그 엔티티가 **빠짐** — 덜 찾음 | 낮음 |
| range 위반 | 잘못 붙은 관계가 답에 **섞일 수 있음** — 틀리게 찾음 | 상대적으로 높음 |

실제로 test-ontology2 는 range 위반이 10건 이상 남은 상태에서도 검색 품질이 쓸 만했다.

### 지금 더 큰 위험 — 편집이 바로 서비스에 반영된다

현재는 **편집기에서 저장하는 순간 서비스 검색에 반영**된다 (스키마 저장, 규칙, 리플레이 모두 즉시).
실험하다 잘못 저장하면 사용자에게 바로 영향이 간다. 운영 중인 KB 는 아래를 지킨다.

- 큰 변경(재유도, 많은 이동·삭제, 재추출)은 **테스트 KB 에서 먼저** 해 본다.
- 평가 질문 세트가 있는 KB(예: 물리학사 test-ontology3)는 재유도를 **미리보기(dry-run)** 로만 보고, 적용 전후 평가를 **2회 이상** 돌린다 (1회 측정은 ±3점 흔들림).
- 잘못 저장했으면 편집기 **이력 → 되돌리기**, 트리플 편집·멤버 지정·병합은 Documents → 스키마 정렬 **규칙 목록에서 삭제** 후 재정규화.

### 권장 구조 (미구현 — 다음 과제)

1. **초안 / 게시 분리**: 편집·이동·삭제·재추출은 초안에만, 서비스는 게시된 버전을 쓴다. "게시"로 넘기고, 이전 게시 버전으로 되돌릴 수 있게. (그래프 데이터를 두 벌 관리해야 해 작업량이 가장 큼)
2. **게시 전 품질 점검**: 위반 수·누락 수·일치율·고립 클래스·정의 빠진 속성을 현재 버전과 비교해 보여 주고, **나빠지면 경고**(막지는 않음). KB 별 기준(예: 일치율 ≥60% 관계 비율)을 두면 통과 여부 표시. 평가 세트가 있으면 게시 전에 돌려 점수를 함께 표시.
3. **검색 쪽 표시**: 일치율이 낮은 관계로 답했을 때 Execution Log 에 "이 관계는 데이터 일치 58%" 처럼 표시.

## 2. 스키마와 맞지 않는 트리플 때문에 잘못된 답을 하지는 않나?

**할 수 있다.** 다만 range 위반만이 원인은 아니다.

### 잘못된 답이 나올 수 있는 경우

| 경우 | 예 | 데이터 검증에 잡히나 |
|---|---|---|
| ① range 위반 트리플이 근거로 쓰임 | "CQRS 채택에 필요한 것은?" → `CQRS —requires→ 멱등성` (의미가 크게 틀리진 않음) | 잡힘 |
| ② 방향이 뒤집힌 트리플 | `Alistair Cockburn —참고_자료→ Hexagonal` → "Cockburn 의 참고자료는?" 에 Hexagonal | 일부 (domain 위반일 때만) |
| ③ 분류가 틀린 멤버 | 예전 '암'·'빛' 이 Person → "인물 목록" 에 암·빛 | 안 잡힘 (멤버 자체가 틀림) |
| ④ **스키마에는 맞는데 사실이 틀린 트리플** | `아인슈타인 —제안함→ 양자역학` (형식은 맞고 사실은 틀림) | **안 잡힘** |

**④가 핵심이다.** 데이터 검증은 "스키마 약속을 지키는가"를 볼 뿐 "사실이 맞는가"는 모른다.
**위반이 0건이어도 틀린 답은 나올 수 있고, range 위반은 오류의 일부를 알려 주는 신호일 뿐이다.**

### 지금 있는 안전장치

- **답변 모델은 트리플과 함께 근거 청크 원문을 본다.** 원문과 다르면 바로잡을 여지가 있다 (다만 트리플을 그대로 믿기도 한다).
- **재추출 시 원문 근거 검사**(`is_grounded`): 목적어 핵심어가 원문에 없으면 버린다 — 지어낸 사실(환각)은 상당 부분 걸러진다.
- **domain 검사**(`check_domain`): 재추출 때 주어 클래스가 domain 과 반대면 방향을 바로잡고, 다르면 버린다.
- 물리학사 평가에서 **없는 사실을 묻는 문항**(negative)은 계속 3/3 이었다 — 근거 없는 답을 지어내지 않는다.

### 더 줄이는 방법 (미구현 — 다음 과제)

1. **검색 단계에서 위반 트리플 표시** (①, 비용 없음): 그래프 검색 결과의 트리플을 range 와 대조해 위반이면 답변 컨텍스트에
   "스키마 불일치 — 원문으로 확인" 표시를 붙이고, 원문만 근거로 쓰게 한다. 제외/표시는 KB 설정으로.
2. **답변 프롬프트 규칙** (②④): "트리플과 근거 청크 원문이 다르면 원문을 따르고, 원문에 없는 내용은 답하지 마라" —
   원문이 맞는 한 추출 오류가 답으로 새는 것을 줄인다.
3. **평가로 확인**: 1·2 적용 전후로 물리학사 39문항(2회)·test-ontology 질문을 돌려 틀린 답이 실제로 줄었는지 측정.

③④는 데이터 검증으로 안 잡히므로 **평가 질문 세트**로만 확인할 수 있다 — 위의 "게시 전 평가"가 이 역할이다.

## 운영 체크리스트

| 언제 | 할 일 |
|---|---|
| 스키마를 크게 바꾸기 전 | 테스트 KB 에서 먼저. 평가용 KB 는 재유도 미리보기만 |
| 정의·방향을 고친 뒤 | 트리플 목록에서 **재추출 테스트** → 효과 확인 → 저장 → 전체 재추출 |
| 재추출 뒤 | 편집기 상단 **"재추출 뒤 정리"** 로 새 멤버 누락 정리 (주기: 정의 수정 → 재추출 → 정리) |
| AI 추천 반영 전 | 처리안을 근거 청크와 대조, **효과 미리보기** 후 승인. 포함 관계 이름 병합('확장성 ← 확장성 요구')·원문을 덜 읽은 삭제는 거절 |
| 데이터 검증 수치 | range 위반은 **틀린 답 위험**이 있으니 우선 처리, 멤버 누락은 **덜 찾는 문제**라 다음 순위 |
| 답변 품질이 의심될 때 | Execution Log 에서 쓰인 트리플 → 트리플 목록에서 근거 청크 확인 → 이동·삭제 또는 정의 수정 |
| 평가 세트가 있는 KB | 변경 전후 평가 2회 이상, 사실 재현율(`results/fact_recall.py`) 함께 |
