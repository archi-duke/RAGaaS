# 다단계 질문 — 홉별 결정적 체인 검색 (mode H)

## 1. 문제
물리학사 평가(docs/datasets/physics-history)에서 다단계 질문 10개는 세 단계 모두 0/10 이었다.
- 승격 전
- 자동 승격
- 시드 승격 — 정답 사실의 79% 가 그래프에 시드 관계 이름 그대로 있는 상태 (docs/design-graph-promotion.md §8)

그래프에 답이 있는데 못 찾는 이유는 라우팅에 있다. 다단계로 판정된 질문은 전부 C(LLM 이 SPARQL 을 통째로 생성) 로 간다.
- C 는 관계 이름·방향·엔티티 URI 를 한 번에 맞혀야 하므로 한 곳만 틀려도 0건이 된다.
- 재시도 포함 문항당 1~2분이 걸린다.
- 결과 트리플과 근거 청크의 연결도 약하다.

## 2. 설계
단일 홉에서 이미 검증된 방식을 홉마다 반복한다. 관계를 고정한 SPARQL 로 트리플을 찾고, 그 트리플의 근거 청크로 답한다.

1. **관계 어휘** (닫힌 집합)
   - 문서 그래프의 관계 이름과 건수.
   - 승격 스키마(active)가 있으면 속성의 정의와 domain → range 를 붙이고 앞에 싣는다.
   - 건수 1인 관계는 뺀다.
2. **체인 계획** (LLM 1회): 질문 → `{start, hops: [{relations(1~3), direction(out|in), expect}], final_relations}`
   - `start`: 질문에 이름이 나온 고유명 하나.
   - `direction`: 현재 노드가 주어면 out, 목적어면 in.
   - 연도·국적 같은 조건은 `expect` 에만 적고 SPARQL 필터로 걸지 않는다. 후보를 모두 모으고, 근거 청크를 보고 답변 LLM 이 고른다.
     추출 그래프에는 시간 정보가 일정하게 들어 있지 않아서, 필터를 걸면 오히려 정답이 빠진다.
   - `final_relations`: 마지막 노드에 여러 가지를 묻는 경우 (예: "어떤 원리를 제안했고 몇 년에 수상했나").
   - 체인으로 표현할 수 없는 질문(같은 해 비교, 기간 계산)은 `chainable: false` → C.
3. **검증**: 어휘에 없는 관계는 버린다. 쓸 관계가 없는 홉이 있으면 계획 전체를 무효로 한다 → C.
4. **실행** (결정적, 홉마다 SPARQL 1~2회)
   - `VALUES ?s|?o { 프론티어 }` + `VALUES ?p { 관계 }` + s-p-o 정확 일치 statement 의 근거 청크.
   - 0건이면 같은 관계를 반대 방향으로 한 번 더 시도한다 (추출 시 주어·목적어 뒤바뀜 대비).
   - 다음 프론티어 = 결과의 리소스 노드 (최대 15개).
   - 첫 홉이 0건이면 C 로 넘긴다. 중간에 끊기면 도달한 범위의 근거로 답하고, 리포트에 경고를 남긴다.
5. **근거 청크 순서**: 홉별로 번갈아 고른다. top_k 안에 모든 홉의 근거가 들어가야 체인을 따라 답할 수 있다.

## 3. Execution Log 리포트
3/5 단계에 `mode=H(다단계 체인 — 홉별 관계 고정 조회)` 를 표시하고, 홉마다 한 줄씩 남긴다.
```
· 홉1: 노드 1개 ←[발견함]← 트리플 2건, 다음 노드 2개 — 기대: 인물 | 다음: 하인리히 헤르츠, …
· 홉2: 노드 2개 ←[지도교수_of]← 트리플 1건, 다음 노드 1개 — 기대: 박사 지도교수 | 다음: 헤르만 폰 헬름홀츠
· 홉3: 노드 1개 →[제안함]→ 트리플 3건, 다음 노드 3개 — 기대: 1847년에 제안된 법칙
```
SPARQL 은 홉별 쿼리를 `# ---- next hop ----` 로 이어서 보여 준다.

## 4. 라우팅
다단계 판정(분석기 multi_hop / hop_count ≥ 2 / '의' 2회 이상) → H 시도 → 다음 경우에만 C 로 넘긴다.
- 계획 불가
- 출발 엔티티 미연결
- 첫 홉 0건

## 7. 보강 (2026-11-15, 설계 검토 반영)
§6 의 남은 실패를 다시 실행해 추론 과정과 그래프를 직접 확인했다. 원인은 다단계 판정이 아니라 대부분 **엔티티 링킹**과 **같은 대상의 노드 분열**이었다.

### 7.1 링킹 — 성(姓)만 쓴 질문 (`entity_linking.score_candidate`)
- 증상: '아인슈타인' → `아인슈타인을_게으른_개_라고_불렀다`, '보어' → `보어_원자_모형`, '슈뢰딩거' → `슈뢰딩거_방정식`, '뉴턴' → `뉴턴_역학`.
  - 접두 일치(60점)가 토큰 포함(40점)을 이기고, 관계 수 보너스가 8점에서 잘려 인물 노드(관계 21개)가 밀렸다.
- 수정:
  - **핵어 일치(75점)**: 질문어가 후보의 마지막 토큰과 같다 ('보어' ↔ '닐스_보어'). 한국어·영어 복합 명사는 핵어가 끝에 오므로 그 후보가 곧 질문어가 가리키는 대상이다.
  - **수식어 일치(50점)**: 질문어가 복합어의 앞 토큰 ('보어_원자_모형' 은 모형이다).
  - **글자가 이어 붙은 접두(35점)**: 조사로 이어지는 문장 노드, 다른 복합어.
  - 관계 수 보너스: 로그 스케일, 최대 18점 (`degree_bonus`).
- 체인 출발점은 링킹 상위 후보 3개를 순서대로 시도해 **첫 홉이 성립하는 후보**에서 출발한다. Execution Log 의 '조정' 줄에 남긴다.

### 7.2 동일 엔티티 묶음 (`entity_linking.equivalent_names`, `fuseki._equivalent_uris`)
- 증상: `소속 빈_대학` 은 '볼츠만'(관계 17개)에 있는데 질문은 '루트비히_볼츠만'(2개)에 연결된다. '양자_전기역학' / '양자전기역학' 도 두 노드다.
- 검색할 때 앵커와 체인 프론티어를 같은 대상의 노드들로 넓힌다. 확실한 경우만 묶는다.
  1. 구분자 제거 후 이름이 같다.
  2. 성 ↔ 전체 이름: 한 토큰 이름이 2~3토큰 이름의 마지막 토큰과 같다. 단,
     - 둘 중 하나라도 인물이 아닌 유형이면 묶지 않는다.
     - 같은 성의 전체 이름이 둘 이상이면 묶지 않는다 ('플랑크' ↔ 막스·에르빈).
- SPARQL 은 `VALUES ?anchor { … }` 로 묶음 전체를 고정한다. 관계 고정·근거 청크 조인은 그대로이고, 이웃을 통째로 모으지 않는다.
- 링킹 줄에 "동일 엔티티 n개 함께 조회: …" 로 표시한다.
- 근본 해결은 추출 단계의 이름 정규화(재추출)다. 이 묶음은 검색 시 보정이다.

### 7.3 체인 실행기
- **계보 관계는 양방향**: domain = range 인 비인물 관계(계승_발전, 일반화함, 근사_극한 …)는 이름의 자연스러운 읽기와 정의 방향이 엇갈려, 그래프에 두 방향이 섞여 있다. 처음부터 양방향(↔)을 조회하고, 방향은 근거 청크로 답변 LLM 이 판단한다.
  - 인물 → 인물(지도교수_of)은 방향이 뜻을 가르므로 제외한다.
- **방문 노드 제외**: 다음 프론티어는 트리플에서 현재 프론티어가 아닌 쪽 끝이다. 이미 거친 노드는 뺀다 (홉2 가 출발점으로 되돌아오던 Q18).
- **끊긴 홉 재선택 (체인당 1회)**: 계획한 관계가 양방향 모두 0건이면, 프론티어 노드에 실제로 달린 관계 목록(관계·방향·건수·예시)을 보여 주고 LLM 이 대신할 관계를 고른다 (닫힌 집합).
  - 예: Q09 의 `전자기파_실험` 에는 '확인함' 이 없고, `하인리히_헤르츠 —확인함→ 맥스웰_방정식` 으로 들어 있다.

### 7.4 라우팅
- 유형 질문(class_query)이라도 분석기가 hop ≥ 2 로 본 질문은 체인을 먼저 시도한다. 안 되면 유형 경로로 간다 (Q10).
- 체인이 안 되면 바로 C 로 가지 않는다. 앵커 관계 조회(A/B)를 먼저 해 보고, 근거가 있으면 경고와 함께 쓴다.
- **E (앵커별 관계 조회)**: 두 엔티티 사이에 직접 관계가 없으면(pair 0건) 앵커마다 A/B 로 조회해 합친다. 근거 청크는 앵커별로 번갈아 고른다.
  - 대상: "같은 해인가", "몇 년 걸렸나" 형 비교·계산 질문 (Q23·Q26). 비교·계산은 근거 청크로 답변 LLM 이 한다.
- C(LLM SPARQL 생성)는 마지막 경로다. 재시도를 2회에서 1회로 줄였다.
  - 근거: 재실행에서 C 로 끝난 8문항 중 정답이 1개였고, 문항당 1~6분이 걸렸다.

### 7.5 재추출 (P4)
- 재추출 프롬프트에 'A | 속성 | B' 정의의 자리 그대로 쓰라는 예시를 넣었다 (`계승_발전`: "B는 A를 이어받아" → subject=A).
- 클래스를 아는 멤버로 domain·range 를 검사한다 (`schema_reextract.check_domain`).
  - 주어·목적어 클래스가 정확히 (range, domain) 이면 뒤집힌 것으로 보고 바로잡는다.
  - 주어 클래스가 domain 과 다르면 버린다 (예: '드브로이(인물) —계승_발전→ 광양자_가설').
    - 처음에는 out_of_schema 표시만 했으나, 저장 단계가 out_of_schema 도 같은 관계 이름으로 넣어 그래프가 오염되므로 제외로 바꿨다.
- 목적어의 핵심 토큰이 원문 청크에 절반 이상 없으면 버린다 (`is_grounded`). 허용 값 어휘와 연도 숫자는 예외다.
  - 대상: Q39 같은 스키마 맞춤 환각 ("1931년 세상을 떠났다" → `수상함 → 1931년도_노벨_물리학상`).
- 재추출 전 기준: 사실 재현율 155/197, `계승_발전` 3/11.

### 7.8 응답 시간 (2026-11-15)
평균 42초의 주원인은 GLM 사고 모드였다. GLM 은 기본이 사고 모드인데 두 호출에 끄는 옵션이 빠져 있었다.
- 질문 분석(`graph._analyze_and_extract`): 다단계 질문에서 33~37초 → 3~4초.
- C 경로 SPARQL 생성기(`sparql_generator`): 1회 80초 → 11초. 동기 호출이라 그동안 이벤트 루프 전체가 멈췄다 → `asyncio.to_thread` 로 분리.
- 결과 (1회): 28/39 (점수 변화 없음), 평균 42초 → **12.2초**, 중앙값 11.3초, 최대 44초(Q21, C 경로).
- 남은 지연: 클래스 카탈로그의 동일 엔티티 판정 LLM 5회(캐시 5분, 빈 캐시에서 약 35초), 게이트 LLM 동기 호출, C 경로 자체.
- 실행 로그의 '벡터 저장소에 본문 없음' 은 top_k 밖 청크를 잘못 표시한 것이었다 → 'top_k 밖 (답변에 미사용)'.

### 7.9 그래프로 답할 수 없으면 문서 검색 (V, 2026-11-15)
결정적 경로(A/B/P/H/E)가 모두 근거 청크를 못 찾으면 LLM SPARQL 생성(C) 대신 문서(벡터) 검색으로 답한다.
- 근거: C 는 문항당 40초 이상이었고, 3회 평가에서 C 로 간 문항 가운데 정답은 1회뿐이었다.
- Execution Log: `mode=V(그래프로 답할 수 없음 → 문서 검색)` 와 앞 경로가 실패한 이유를 함께 쓴다. 근거 청크는 "그래프 근거 아님" 으로 표시한다.
- 설정: `graph_fallback="llm_sparql"` 이면 기존 C 경로를 쓴다 (기본 `vector`).
- 대체 검색은 KB 의 임베딩 설정을 넘겨야 한다 (전역 기본값은 키가 없어 0건이 나왔다).
- 함께 고친 지연
  - 유형 카탈로그의 동일 엔티티 판정 LLM 결과를 파일(`data/cache/equiv_llm_cache.json`)에 보관 → 재시작 직후 첫 요청의 약 35초 제거.
  - 게이트 LLM 동기 호출을 `asyncio.to_thread` 로 분리.
- 결과 (1회): **30/39**, 평균 **10.2초**, 최대 17초, 오류 0.
  - V 로 간 문항: Q35 오답→정답, Q21·Q36 오답→부분 정답, 없는 사실 Q37·Q39 는 "정보 없음" 그대로 정답.
  - Q09·Q14·Q22·Q25 의 변화는 V 와 무관한 경로(H·A)의 실행 간 흔들림이다.
- 주의: V 로 맞힌 답은 그래프 근거가 아니다. 그래프 품질 지표로 볼 때는 V 문항을 따로 센다.
